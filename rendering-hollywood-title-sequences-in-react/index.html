Rendering Hollywood
Title Sequences in React

One React app recreates the most recognizable openings in film — some in pure code, some by driving a 3D engine — then ships a finished 4K video to your inbox in minutes.

Nihey TakizawaCTO, Kassel Labs9 min read

Since 2015 we've let people drop their own name into the opening of Star Wars, Stranger Things, Loki and dozens more — over a million videos and counting. The magic trick our users see is simple: type some text, get back a broadcast-quality title sequence. The engineering underneath is anything but. This is a look at how those intros are actually rendered — and why we ended up with two completely different pipelines living in the same codebase.

Every intro we build has to satisfy three constraints at once. It has to be pixel-faithful to a sequence people have seen a hundred times (the uncanny valley is brutal here). It has to be fully parameterized — arbitrary user text, arbitrary length, sometimes swapped images and colors. And it has to render unattended, at 4K, fast enough that nobody's waiting around. Those constraints pushed us toward Remotion — React that renders to video, frame by frame — as the backbone. But not every title sequence wants to be pure code.

01 — Pure RemotionThe Loki title: fourteen fonts per letter

The Loki main title has a signature move: each letter flickers through a stack of mismatched typefaces before settling — a nod to the show's identity-in-flux theme. Recreating that in After Effects is a keyframing nightmare. In code, it's a loop.

Every character cycles through 14 eclectic typefaces sitting on a procedurally-grained, glowing plate. Rather than render live text (slow, and font metrics drift), each glyph is baked per-character into sprites ahead of time. The morph then just cross-dissolves between sprites on a schedule driven by useCurrentFrame().

That blank-sprite detail is the kind of thing you only hit at scale: some of the fonts genuinely don't contain certain accented or exotic glyphs, so naively morphing would flash an empty box mid-animation. Detecting and skipping missing glyphs keeps the effect clean for a user whose name happens to be Þór. The theme audio is muxed in from a separate track, and — crucially — there's no pre-render step. Loki is Remotion start to finish.

02 — Blender + RemotionThe Disney castle: when code isn't enough

The Disney intro is a different beast. That title isn't flat — it's polished 3D chrome lettering with real bevels and reflections, sitting in front of the castle. You can fake a lot in CSS and SVG, but you can't fake that. So we don't.

Instead, Blender 2.79b renders only the title and subtitle — as 3D text — out to a transparent PNG. Then Remotion takes over: it reads that PNG, measures where the ink actually is, and composites it over a pre-baked castle background video.

The interesting step is #3. Because the user's text can be any length, we don't know in advance how big the rendered title will be. So we scan the PNG's alpha channel to find its bounding box, and from that compute the composite layout — position, scale, and fade timing — so the title always sits correctly against the castle regardless of whether it says "Jo" or "Alexandria-Katherine". Pure math, no manual tweaking per order.

The user types the text. Blender sculpts the letters. Remotion measures the ink and places it. Nobody touches a keyframe.

Timing is locked to the original: 742 frames at 24000/1001 fps — the same ~30.95 seconds as the reference render, down to the frame. Getting this exact matters more than it sounds; even a few frames of drift makes a familiar sequence feel subtly wrong.

Why 2.79b specifically? Later Blender releases changed the Python API, and our render script targets the 2.79 bindings. Pinning the engine version is part of the contract.

03 — The 4K trickScale the frame, not the canvas

Here's a subtlety that took a beat to get right. Both shows lay their text out in fixed 1080p pixel coordinates — a title's vertical center, sprite sizes, everything is authored against a 1920×1080 grid. So how do you render 4K without re-authoring every layout?

The naive move is to enlarge the canvas to 3840×2160. But then all those fixed pixel positions are suddenly in the top-left quadrant, and the layout falls apart. The fix is to keep the native canvas and scale the whole frame up instead:

Because we scale the frame rather than the canvas, every fixed-pixel layout stays centered and correct — it's just rendered at twice the density. Disney goes one further and tells Blender to render its text at resolution_percentage: 200, so the 3D chrome is natively 4K rather than an upscaled 1080p asset. (Below-native targets take the opposite path: supersample at native, then a Lanczos downscale in ffmpeg.)

04 — OrchestrationFrom "Pay" to inbox, on one worker

None of this runs on request-response. Rendering a 30-second 4K intro — especially the Blender leg — is far too heavy to block an HTTP handler. So delivery is a queue.

A long-lived BullMQ worker drains a single render-remotion queue at concurrency 1 (rendering is CPU/GPU-bound; parallelism here just thrashes). When a customer pays, the admin enqueues a job for any intro type flagged auto_render. The worker then walks a fixed four-step delivery contract:

MARK
status → rendering
→
RENDER
Remotion (+ Blender for Disney)
→
UPLOAD
signed S3 PUT
→
NOTIFY
status → finished, email

Marking rendering first isn't cosmetic — it lets a reaper process recover jobs that die mid-render instead of leaving a paying customer stuck. And the S3 upload carries an x-amz-acl: public-read header that is emphatically not optional: forget it, and the object uploads privately, so the customer's finished video greets them with a 403. (Ask me how I know.) The whole thing is Dockerized with Blender and a headless Chrome baked into the image, so a deploy is a single container.

05 — Try the engine yourselfThe same compositions, live in your browser

Here's the part that ties it together: those Remotion compositions aren't locked away on the render farm. The same code that renders our server-side title cards also runs client-side via @remotion/player, which is exactly what powers our free font generators. Type into one and you're driving the identical composition — it just exports a PNG in-browser instead of an MP4 on the queue.
